# План разработки MVP: один Cocoon worker с pipeline

Дата: 2026-10-04. Статус: шаги 1–4 и 6–11 проверены согласно отчётам; шаг 5 отложен, шаги 12–13 впереди. SGLang и vLLM PP=2 интегрированы с Cocoon и отдельно проверены на двух RTX.

Архитектура и ограничения описаны в [pipeline-design.md](/Users/ms/Developer/cocoon/pipeline-design.md). Весь pipeline представлен одним worker; внутренние стадии используют один выбранный backend — SGLang или vLLM — и обмениваются данными через WireGuard. Proxy сохраняет существующий контракт запросов и расчётов.

План разделён на 13 проверяемых этапов. Каждый этап даёт отдельное изменение для ревью и воспроизводимую проверку. Если изменение велико, его можно разбить на несколько PR, сохраняя критерии готовности этапа. Ранний GPU-эксперимент должен подтвердить вычислительную основу до крупных изменений агента и deployment.

## 1. Среды разработки и проверки

| Среда | Что проверяем |

| Нативный Mac | HTTP/streaming, ошибки, отмену, буферы, profiles, supervisor, протокол группы, gate и интеграцию с fake-TON |

Большинство изменений имеют проверку на Mac. Построение правильных argv или успешный simulator не заменяют GPU-проверку шагов 2, 10, 11 и 13. Разделение dev и production policies закладывается в шагах 6–7; функциональный MVP работает в явном dev-режиме.

### Существующие нагрузки на GPU

На машинах сейчас могут работать процессы, сервисы, контейнеры или VM, использующие GPU. **Пользователь разрешил выключать эти нагрузки для освобождения GPU: текущие вычисления не важны, сохранять их работу не требуется.** Дополнительное согласование остановки этих GPU-нагрузок не нужно.

Перед экспериментом определить, какие процессы или VM держат устройство, и остановить соответствующую нагрузку, включая её автоматический перезапуск при необходимости. Это разрешение относится к освобождению GPU на двух указанных машинах.

### Перевод GPU в PCIe passthrough

Предоставленная пользователем команда выполняется на нужном GPU-хосте после освобождения устройства:

```bash
sudo virsh -c qemu:///system nodedev-detach pci_0000_01_00_0 --driver vfio-pci &&
sudo virsh -c qemu:///system nodedev-detach pci_0000_01_00_1 --driver vfio-pci &&
lspci -nnk -s 01:00
```

Команда переводит PCI-функции `01:00.0` и `01:00.1` на `vfio-pci`; по выводу `lspci` проверить фактический driver binding. Это подготовка к передаче устройства VM. Создание VM и назначение ей PCI-устройств выполняются отдельно.

Для первого эксперимента с SGLang/vLLM в контейнерах непосредственно на хосте GPU должна быть доступна хостовому NVIDIA-драйверу. Passthrough нужен при переходе к испытаниям в VM; его не включаем как обязательный предварительный шаг контейнерного запуска.

### Шаг 2. Ранний эксперимент с GPU

**Статус: выполнен (2026-10-04).** Добавлен dev-стенд [experiments/gpu-pipeline](experiments/gpu-pipeline/README.md): закреплённые SGLang/vLLM и модели, отдельные WG namespaces/ключи, запуск, измерения, проверки API/отказов и cleanup. На двух RTX прошли шесть GPU-запусков и девять локальных тестов. Для каждого backend сравнение Qwen3-0.6B PP=1/PP=2 дало одинаковые fixtures и logprobs; Qwen3-14B BF16 работает PP=2 без CPU offload при context limit 4096 и concurrency 1.

Подтверждены NCCL Socket через `wg0`, участие обоих rank, длинный prefill (2070 prompt tokens) и ошибочное завершение активного запроса при смерти rank 1. Итоговый SGLang-профиль отключает chunked prefill из-за обнаруженной KV-ошибки; vLLM ограничивает RPC deadline до 30 секунд. Неудачные исходные профили и повторные проверки сохранены в [отчёте](experiments/gpu-pipeline/REPORT.md). После проверки тестовые процессы, туннели и ключи удалены. Это dev-проверка без CC, не квалификация production deployment.

**Повторная полная проверка после подготовки хостов:**

```bash
python3 experiments/gpu-pipeline/pilot.py matrix
```

**Изменение для ревью:** минимальные скрипты запуска SGLang и vLLM на двух машинах: PP=2, TP=1, WireGuard и закреплённые версии. Полноценные agent/deployment пока не требуются; настройки стенда и ключи тестового туннеля отделены от production profile.

**Проверка:** две RTX. Сначала Qwen3-0.6B, сравнение с PP=1 того же backend/version/dtype; затем Qwen3-14B BF16, начальный context 2048–4096 токенов, один активный запрос. Проверить фактическое участие обеих стадий, Socket transport через WireGuard и отказ запроса при потере второй стадии. Сохранить версии, конфигурации, расход памяти и измерения сети/инференса.

**Готово, когда:** для каждого движка есть воспроизводимый результат PP=2 через туннель и отчёт о capacity целевой модели. Проблема одного движка явно зафиксирована и не скрывается переключением на другой. Крупную интеграцию продолжаем после подтверждения выбранной основы.

Локально на Mac можно проверить генерацию конфигурации и скрипты, а в Linux VM — тестовую сеть. Работа настоящего CUDA/NCCL подтверждается только GPU-стендом. Равенство seed не требует побитового совпадения ответов разных движков; корректность каждого PP сравнивается прежде всего с его PP=1.

### Шаг 3. Корректное завершение HTTP-запросов

**Статус: выполнен (2026-10-04).** Разделены успешное завершение и ошибка HTTP transport; JSON проверяется целиком, SSE terminal удерживается до полного HTTP framing. HTTP 4xx/5xx, backend error events, неполный JSON/SSE и обрывы завершают запрос через ошибку с нулевым расчётным usage. Client HTTP adapter при ошибке после headers закрывает поток без финального chunk. Обычные JSON/SSE и encrypted responses сохраняют обработку content/usage; пользовательская причина backend error также шифруется и не попадает в plaintext TL error.

**Команда проверки:** `python3 benchmark/smoke-local.py --scenario all`. Прошли 23 сценария / 37 запросов, включая 9 encrypted: 12 успешных запросов оплачены по 134 adjusted tokens, 25 неуспешных — по 0. Для каждого проверены счётчики worker/proxy/client, балансы и payment notifications, единичное завершение, освобождение reservation и cleanup. Прошли 10 C++ transport/framing случаев, C++ JSON/SSE/usage/encryption tests и Go backend tests с race detector. После финального исправления UTF-8 error event повторно прошли C++ тесты и затронутый сквозной SSE error в обоих режимах. Подробности, воспроизведение и границы проверки — в [STEP3-REPORT.md](pipeline/STEP3-REPORT.md).

**Изменение для ревью:** исправить различение успешного ответа, ошибки транспорта и оборванного JSON/SSE в существующем worker. Сохранить обычную обработку успешных ответов.

**Проверка:** Mac со стендом шага 1. Обрывы до headers, после headers и после нескольких токенов; HTTP errors; неполный JSON/SSE; обычные JSON/SSE ответы.

**Готово, когда:** незавершённый ответ даёт ошибку, отсутствуют ложный success, успешный billing и двойное завершение. Обычные ответы и usage продолжают работать.

### Шаг 4. Отмена и deadlines

**Статус: выполнен (2026-10-04).** Добавлены слабый cancel handle, сериализация I/O/отмены через strand и абсолютный дробный HTTP deadline. Worker владеет registry по connection/request ID и отменяет upstream при timeout, ошибке postprocessing, остановке actor и закрытии proxy connection. Повторные cancel/finish безопасны; socket закрывается до terminal callback, позднее завершение не удаляет другой actor с тем же ID. `/jsonstats` показывает число активных запросов.

**Команда проверки:** `python3 test/test-worker-cancellation.py --build-dir build/local`. Прошли 17 C++ случаев / 207 запросов, 10 прежних HTTP framing tests и 74 сквозных запроса: 70 отмен/ошибок и четыре успеха. Все 70 backend-сокетов закрылись со стороны worker до остановки fixture; registry после каждой серии пуст. Два падения proxy освободили по восемь запросов за 0,108 и 0,110 с, тот же worker обслужил запрос после каждого restart. Восстановление проверено после подтверждённого сохранения баланса; crash до сохранения выявил отдельную границу P4-02. Полная регрессия `python3 benchmark/smoke-local.py --scenario all`: 23 сценария / 37 запросов, включая девять encrypted, без ложного success/billing и утечек тестовых процессов. Подробности и артефакты — [STEP4-REPORT.md](pipeline/STEP4-REPORT.md).

**Изменение для ревью:** cancel handle HTTP-клиента, учёт активных запросов и отмена при timeout или потере соединения с proxy.

**Проверка:** Mac. Зависший backend, истечение deadline, disconnect proxy, гонки между завершением и отменой, повторная отмена.

**Готово, когда:** запрос и его HTTP-соединение освобождаются за ограниченное время; после серии отмен не остаются активные запросы и соединения. Повторная отмена безопасна.

Сквозная мгновенная отмена при закрытии HTTP-клиента на другом конце Cocoon не входит в этот шаг: текущий внешний TL-протокол не предоставляет отдельный request cancel. Проверяем доступные worker сигналы и deadlines.

**Изменение для ревью:** лимиты очередей и реакция на медленного получателя, включая участок worker → proxy и постановку payload в actor mailbox.

**Проверка:** Mac. Backend быстро генерирует большой поток, downstream читает медленно или перестаёт читать. Проверка собирает queued bytes и расход памяти.

**Готово, когда:** объём буферов ограничен, запрос приостанавливается или завершается предусмотренной ошибкой; квоты освобождаются после завершения/отмены. Нет неограниченной очереди перед транспортным буфером.

### Шаг 7. Формирование группы

**Статус: выполнен (2026-10-04).** Два `pipeline-agent-dev` согласуют группу по mutual TLS 1.3: Hello/challenges, config digest, полный roster, Prepare/Commit, heartbeat и leases. Peer public key/image hash проверяются существующими RA-TLS primitives Cocoon с отдельной dev policy; network public keys генерируются агентами и привязываются к этим identities. Backend запускается после Commit; readiness появляется после warmup обоих симуляторов. Отказы закрывают группу; после подтверждённого cleanup допускаются две повторные попытки с новым epoch и ключами. Истечение сертификата закрывает активную TLS-сессию до окончания его срока.

**Команда проверки из корня репозитория с настроенным CMake build:**

```bash
python3 test/test-pipeline-group.py --build-dir build/local
```

Прошли C++-проверки протокола и настоящих TLS handshakes, включая неправильные image/key binding, отсутствие evidence, просроченные сертификаты и запрет dev evidence в production policy. Прошли 13 интеграционных сценариев: согласование/stop, config mismatch, неверный и дублирующийся участник, replay/старый epoch/смена payload, невозможность продлить lease повторным Commit, неудачный warmup, падение backend, пауза head, потеря member, ограниченные retries, отсутствие клиентского сертификата, oversized frame и истечение активного сертификата. Проверены очистка процессов/sockets и смена epoch/network keys при восстановлении. Дополнительно прошли все 16 локальных интеграционных тестов supervisor и обычный single-worker smoke Cocoon.

Инструкции и примеры конфигураций — в [pipeline/README.md](pipeline/README.md#два-агента-с-mutual-tls--шаг-7). Dev evidence остаётся синтетическим, endpoints ограничены loopback, `hardware_attested=false`, `network_setup=simulated`. `READY` подтверждает согласование и локальные warmup двух симуляторов; сквозной PP inference, WireGuard, worker gate и real CVM deployment ещё не реализованы этим шагом. HTTP lifecycle и лимиты существующего worker проверяются отдельно в шагах 3–5.

**Изменение для ревью:** head/member, config digest, roster, epoch, Prepare/Commit, heartbeat и leases. Настоящий mutual TLS с тестовой attestation policy; привязка network public keys к проверенным identities.

**Проверка:** два агента на Mac. Успешная группа, неверный участник, разные profiles/backends, дубликат rank, повтор сообщений, старый epoch, потеря head/member. Отдельно проверить запрет принятия dev evidence production policy.

**Готово, когда:** группа запускается только после согласования всех участников, старые сообщения не меняют новый запуск, потеря участника закрывает группу, восстановление создаёт новый epoch.

Тестовые удостоверения проверяют протокол и ветки policy; аппаратная TDX/GPU-аттестация остаётся отдельной проверкой.

### Шаг 8. WireGuard и сетевая изоляция

**Статус: выполнен (2026-10-04), dev-профиль с simulator.** Добавлен `simulator-dev-pp2-wg-v1`: агент настраивает настоящий WireGuard из аутентифицированного roster через локальный helper; backend запускается без capabilities в namespace только с `lo`/`wg0`, без default route. Underlay и engine защищены default-drop firewall. `Commit` ждёт успешных двусторонних encrypted probes; сетевой отказ закрывает группу, а новый epoch допускается только после подтверждённой очистки процессов, namespace, interfaces, kernel keys и firewall. После SIGKILL helper агент использует recovery helper с записью владения, не передавая ему приватный ключ.

Capture во время READY: 150 WireGuard packets, 3 control TCP packets, 0 посторонних IPv4 packets; plaintext marker отсутствует. ### Шаг 9. Один pipeline worker в Cocoon

**Статус: выполнен (2026-10-04).** Head-agent предоставляет loopback HTTP gate к UDS backend текущего epoch. `/v1/models` и admission зависят от готовности всей группы, control lease и локального health. При отказе группы закрываются все её запросы; при disconnect worker закрывается upstream. Worker удаляет клиентские служебные headers, передаёт собственный request ID/остаточный timeout и проверяет `is_disabled()` до создания request actor. Proxy и внешний TL-протокол не изменены.

**Проверка:** `python3 test/test-pipeline-worker.py --build-dir build/local`; в подготовленной VM — `orbctl run -m cocoon-pipeline-net -u root python3 /work/cocoon/test/test-pipeline-worker.py --build-dir /opt/cocoon-build --network`. В каждой среде прошли 17 групп проверок и 15 сквозных Cocoon-запросов: десять успешных по 4 adjusted tokens и пять неуспешных по 0; шесть запросов encrypted. Проверены два одновременных потока при гибели member backend и паузе member-agent/control loss, disabled worker/proxy, закрытое admission, смена epoch, удаление старых backend/sockets и успешный запрос после обоих восстановлений. Прошли отрицательные API/metadata/лимитные тесты, регрессии 16 supervisor / 13 group tests, HTTP cancellation и обычного single-worker JSON/SSE/encryption. Подробности, временные границы и артефакты — [STEP9-REPORT.md](pipeline/STEP9-REPORT.md).

**Изменение для ревью:** head gate подключается к worker. Readiness зависит от всей группы; admission закрывается при её отказе. Вычисления пока выполняет simulator.

**Проверка:** Mac, затем Linux VM. Полный запрос client → proxy → worker → gate; падение member во время streaming; несовпадение readiness; восстановление группы. В fake-TON проверить учёт успешного и неуспешного запроса.

**Готово, когда:** proxy видит один worker, успешный запрос оплачивается один раз, неуспешный получает нулевое расчётное usage. Отказ member прерывает запрос и отключает worker; после восстановления можно обслужить новый запрос без старых ответов/KV state.

P8-02 сохраняется для локального gate/UDS, прав сервисов и упаковки sandbox: служебные HTTP headers не аутентифицируют произвольный guest-процесс. P3-01/P3-02, P4-01/P4-02 и P7-01/P7-03…P7-05 также остаются открытыми либо за пределами MVP согласно их статусам; новый epoch не закрывает reconciliation proxy, ротацию и production attestation.

**Новая работа без конкретных задач и критериев в текущем плане:**

| ID / статус | Что осталось и почему это важно | Где предусмотреть и чем подтвердить завершение |
|---|---|---|
| P9-01 — открыто, до приёмки deployment | **Совместная валидация настроек worker и pipeline-agent.** Общий digest связывает агентов, но model name, `max_active_requests` и коэффициент worker пока задаются отдельно. **Осознанные границы MVP и проверки:** два simulator rank, без реальной математики и GPU/KV; чистое состояние подтверждено новым epoch, новыми процессами и нулевыми synthetic reservations. Native-профиль моделирует сеть; Linux-профиль использует реальный WireGuard между двумя namespace в одной VM. Это не проверка двух CVM, удалённого production proxy или аппаратной конфиденциальности. Backend crash обнаруживается раньше молчащего control peer; для последнего действуют control/lease deadlines. Disabled в proxy распространяется polling, а gate закрывает admission самостоятельно. Автоматических повторов inference нет.

### Шаг 12. Воспроизводимый deployment

**Изменение для ревью:** генерация per-host bundles с profiles, одинаковыми artifacts, endpoints, ресурсами и командами запуска. Обработка частичного запуска и остановки. Для MVP — явный dev-режим; ручной запуск bundle на каждом хосте достаточен.

### Шаг 13. Приёмка MVP

**Изменение для ревью:** единый набор приёмочных сценариев и benchmark-отчёт для обоих backend. Конфигурации и команды воспроизводят результат на стенде.

**Проверка:** две RTX. Большая модель работает как один worker без CPU weight offload; JSON/SSE, usage, отмены, падения, восстановление, память и длительная серия запросов. Измерить TTFT, inter-token latency, throughput и издержки WireGuard. Сравнение с plain TCP разрешено только в отдельном тестовом benchmark на тестовых данных.

**Готово, когда:** оба adapter проходят заявленные сценарии, есть отчёт по поддерживаемым profiles и ограничениям. Скорость зафиксирована измерениями, а не предположением о двукратном ускорении от двух GPU. Результат явно обозначен как функциональный MVP без аппаратной конфиденциальности.

## 4. Что должно сопровождать каждый этап

- Описание изменения: новое поведение, затронутые компоненты и существенные ограничения.
- Одна документированная команда проверки с запуском необходимых зависимостей и cleanup. Команды добавляются вместе с реализацией соответствующего этапа.
- Критерии успеха с assertions и корректным exit code; чтение логов не должно быть единственным способом понять результат.
- Как минимум один существенный сценарий отказа, если этап добавляет поведение при ошибках.
- Для аппаратных проверок — версии, конфигурация и сохранённый отчёт, позволяющие повторить эксперимент.
- Обычный single-GPU worker и существующий пользовательский API продолжают проходить относящиеся к изменению проверки.

**Обязательный раздел при завершении каждого шага — «За скобками реализации шага N».** Его нужно сохранять в этом плане и кратко отражать в итоговом сообщении пользователю. Правило действует для каждого следующего шага и при пересмотре ранее выполненного; для шага 7 раздел заполнен выше.

Раздел должен различать:

- Не реализованное на этом этапе, но уже покрытое конкретным следующим шагом: указать номер и соответствующую проверку.
- Работы, которых нет в плане либо которые упомянуты только в общем виде без задачи реализации и критерия приёмки: указать, чего именно не хватает, последствия, когда нужно предусмотреть работу и как подтвердить её завершение.
- Осознанные ограничения MVP и возможные расширения: явно отметить, требуется ли отдельное решение о включении в scope.

Каждой работе без конкретного этапа присваивается постоянный ID `P<шаг>-<номер>` и статус. Возможные статусы: `открыто`, `включено в шаг N` со ссылкой на его дополненные требования и проверки, `закрыто` со ссылкой на реализацию/результат проверки, `за пределами MVP` с основанием и условием возврата. При продолжении разработки нужно сверять открытые записи прежних шагов; перенесённая работа сохраняет исходный ID. Запись не удаляется только потому, что породивший её шаг выполнен. При включении работы в этап нужно дополнить его задачи и критерии приёмки, а не только поставить номер рядом с записью.

Если новых непокрытых работ не обнаружено, явно написать: «Новых работ вне плана не выявлено», сохранив ссылки на уже запланированный остаток и актуальные ограничения проверки. Этот раздел не заменяет выполнение критериев текущего шага: незавершённое обязательное требование самого этапа нельзя объявлять будущей работой ради статуса «выполнен».

## 5. Порядок и промежуточные результаты

1. Начать с локального стенда и раннего GPU-эксперимента, шаги 1–2. Если вычислительная основа не работает, скорректировать profile/дизайн до крупной интеграции.
2. Шаги 3–4 и 6–11 выполнены. Шаг 5 остаётся отложенным и обязателен перед нагрузочными испытаниями и приёмкой MVP в шаге 13. Стенд шага 1 проверяет HTTP-исправления, шаг 9 добавил сквозные сценарии группы, шаги 10–11 — реальные SGLang и vLLM PP=2 через Cocoon на двух RTX. Перед deployment учесть открытые P8-01/P8-02, P7-02 и P9-01; P3-01/P3-02 сохраняют границы API/readiness, P4-01/P4-02 — сквозной отмены и восстановления расчётов.
3. Шаги 6–9 дают группу с simulator и полный Cocoon-сценарий, проверяемый без GPU. WireGuard проверяется в Linux VM.
4. SGLang подключён и проверен в шаге 10, vLLM — в шаге 11. Оба используют общую логику группы и результаты раннего эксперимента.
5. Шаги 12–13 превращают стенд в воспроизводимый функциональный MVP.

Основные рубежи: после шага 2 подтверждена вычислительная основа; после шага 9 полный Cocoon-сценарий работает с симулятором; после шагов 10–11 работают реальные backend; после шага 13 принят функциональный MVP.

## 6. После функционального MVP

Настоящие TDX/GPU attestation и квалификация confidential deployment выполняются отдельным этапом на подходящем CC-стенде согласно Gate E в техническом дизайне. Потребуются production image/spec, проверка полного GPU ↔ private RAM ↔ WireGuard пути, отказов и производительности для каждого backend profile.

Этот раздел задаёт направление, но ещё не является подробным планом реализации production-поддержки. При его детализации обязательно учесть открытые записи P7-01, P7-03 и P7-04; P7-02 должен быть закрыт уже к приёмке VM deployment. Наличие этого раздела не означает, что шаги 1–13 автоматически реализуют перечисленное.

До этой проверки dev-стенд не публикуется как confidential worker. Протокол группы и backend adapters должны переиспользоваться; разделение dev/production policies, заложенное в шагах 6–7, позволяет добавить настоящую аттестацию без переработки управления группой.
